# Workout Tracker — требования и план реализации для AI-агента

Версия: 1.0 · Дата: 2026-10-03

Документ предназначен для реализации полноценного веб-приложения. Язык документа — русский; интерфейс, сообщения об ошибках, справка и стартовые названия тренировок/упражнений — **английский**. Пользовательский текст можно вводить на любом языке.

## 1. Задача и основные решения

Создать личный дневник тренировок: пользователь составляет программы, выбирает любую из них в любой день, быстро записывает подходы на телефоне, видит визуальный таймер отдыха, календарь и динамику результатов.

Обязательные решения:

- **Svelte + SvelteKit + TypeScript**; совместимые стабильные версии зафиксировать в lockfile.
- **Firebase Authentication с Google Sign-In** — вход в аккаунт. **Cloud Firestore** — хранение данных. Firestore сам по себе не является системой авторизации.
- **Vercel** — целевой хостинг; использовать официальный `@sveltejs/adapter-vercel` и конфигурацию для выбранной версии SvelteKit.
- Responsive mobile-first интерфейс в стиле [infm5/neubrutalism_ui](https://github.com/infm5/neubrutalism_ui). Этот репозиторий содержит Flutter-компоненты; использовать его как визуальный референс и реализовать компоненты на Svelte/CSS.
- Авторизованный пользователь видит только свои данные. Общих тренировок, социальных функций и ролей тренера в MVP нет.
- Единица веса MVP — **kg**; длительность — секунды/минуты, расстояние для временных упражнений — необязательные km.
- Шаблон тренировки, фактически выполненная тренировка и запись отдельного подхода — разные сущности.

Технические основания: [Google Sign-In](https://firebase.google.com/docs/auth/web/google-signin), [SvelteKit / Vercel](https://svelte.dev/docs/kit/adapter-vercel), [Firestore Security Rules](https://firebase.google.com/docs/firestore/security/rules-conditions).

### 1.1. Как трактовать фотографию и пять стартовых тренировок

На исходной фотографии `IMG_6416.jpg` напечатано **шесть** дней: Monday–Saturday; Sunday — отдых. Чтобы выполнить требование «пять тренировок для новых пользователей», принять следующее явно зафиксированное допущение:

1. Автоматически создавать пять шаблонов: **Monday, Tuesday, Wednesday, Friday, Saturday**.
2. Четверг с разминкой, приседаниями, бегом и ходьбой сохранить в этом документе как **дополнительную шестую программу**, без автоматического добавления новым пользователям.
3. Названия дней описывают исходную таблицу, но не ограничивают запуск: Monday можно выполнить в четверг, несколько тренировок можно выполнить в один день.
4. Переносить напечатанные планы, отдых и примечания. Рукописные выполненные веса, повторы, даты и комментарии о конкретных тренировках не создавать как историю новых пользователей.
5. Рукописное уточнение «по одной» у сгибаний ног сохранить как примечание о single-leg variation. Не придумывать отдельные результаты для левой и правой ноги.

Если владелец позже выберет другой состав пяти программ, менять только seed-набор, сохраняя существующие пользовательские данные.

## 2. Границы MVP

В MVP входят: Google login, персональные программы и каталог упражнений, выполнение и редактирование тренировок, визуальный отдых, восстановление активной тренировки, история, отдельный календарь, аналитика, обратимые исключения из аналитики, JSON-импорт, справка по JSON, пять стартовых шаблонов, рабочая конфигурация Firebase и Vercel.

Не включать без отдельного требования: платежи, тренерские аккаунты, публичные профили, AI-генерацию внутри приложения, автоматическое назначение весов, интеграции с часами, push, звук/вибрацию, обязательную установку PWA, планирование повторяющегося расписания. Кнопка копирования инструкции для внешнего LLM не требует API к LLM.

## 4. Вход и первая инициализация

1. Кнопка **Continue with Google** запускает Firebase Authentication. Реализовать выход и восстановление сессии после обновления страницы.
2. До завершения проверки авторизации показывать loading state; не отображать чужой или устаревший профиль на мгновение.
3. Отмена Google-диалога не является критической ошибкой. Ошибки сети/заблокированного popup должны иметь понятное сообщение и повторный запуск.
4. Проверить вход на мобильных Safari и Chrome. Если используется redirect, настроить его по [официальным рекомендациям Firebase](https://firebase.google.com/docs/auth/web/redirect-best-practices), с учётом домена приложения на Vercel и ограничений стороннего хранилища браузера.
5. При первом входе создать профиль, 15 исходных упражнений и ровно 5 шаблонов из раздела 13. История и календарь остаются пустыми.
6. Инициализация должна быть идемпотентной: транзакция с маркером `seedVersion: 1` и стабильными seed-идентификаторами. Два открытых таба, повторный вход и повтор запроса не создают дубли. При ошибке возможен безопасный Retry.
7. Удаление/архивация пользователем стартовых программ не вызывает их восстановления при следующем входе. Обновление seed-файла не перезаписывает пользовательские правки.
8. Первый вход и создание seed-набора требуют сети. Не выдавать частичную инициализацию за успешную.

## 5. Шаблоны и каталог упражнений

### 5.1. Редактор тренировки

Пользователь может создавать, переименовывать, дублировать и архивировать программы; менять порядок упражнений; добавлять и удалять упражнения; редактировать план и отдых. Для перемещения предоставить кнопки Move up / Move down, даже если есть drag-and-drop.

Поля программы: name, description/notes, ordered items, archive state. Название обязательно. Дублирование программы создаёт новую программу, но использует существующие идентификаторы упражнений.

Поддержать три типа задания:

| `kind` | План | Фактический ввод |
|---|---|---|
| `strength` | Число подходов, min/max повторов, отдых | Повторы, вес или поправка веса, необязательная заметка |
| `isometric` | Число кругов, направления, min/max удержания, отдых между кругами | Секунды по каждому направлению, завершение круга |
| `duration` | Целевое время, отдых после блока | Фактическое время, необязательное расстояние |

Для силового упражнения можно задать необязательный стартовый вес. **В seed-программах вес пустой**, потому что фотография содержит результаты конкретного человека, а не универсальные назначения.

Одинаковое упражнение в разных программах выбирается из личного каталога и сохраняет один `exerciseId`. Например, Wednesday Pull-up и Friday Pull-up имеют общую историю упражнения. Строки программы имеют отдельный `itemId`, поэтому одно упражнение можно повторить внутри программы без конфликта.

### 5.2. Что означает вес

Хранить у упражнения `loadMode` и `weightConvention`:

- `external`: фактический неотрицательный внешний вес. Convention: `total`, `per_dumbbell`, `machine_stack` или `as_logged`.
- `bodyweight`: поле `weightKg` означает поправку: `0` — собственный вес, положительное значение — дополнительный вес, отрицательное — помощь. Convention: `bodyweight_adjustment`.
- `none`: вес отсутствует; convention `none`. Для strength можно использовать для упражнений без измеряемой нагрузки.

У гантелей явно показывать **kg per dumbbell**, у штанги — **kg total**. Для `as_logged` показывать **kg as logged** и разрешить пользователю уточнить оборудование. Не выдумывать оборудование, которого нет в исходной таблице: это особенно относится к French Press, Calf Raise и Chest-Supported Row.

Для подтягиваний использовать удобный переключатель **Bodyweight / Added weight / Assistance** и неотрицательное поле величины; приложение переводит это в 0/плюс/минус при сохранении. Не требовать ввода знака минус с телефонной клавиатуры.

Переименование упражнения сохраняет его идентичность. Смена `kind`, `loadMode` или convention при наличии истории создаёт новый вариант упражнения: нельзя объединять несовместимые измерения в одном графике. Архивирование скрывает из выбора новых программ, но сохраняет историю.

### 5.3. История не зависит от будущих правок

При старте создавать snapshot названия и состава программы, заданий, отдыха, названий упражнений и соглашений о весе. Изменение шаблона влияет на будущие сессии. Существующая сессия, включая активную, использует собственный snapshot.

Архивирование/удаление шаблона не удаляет выполненные тренировки. В MVP кнопку удаления шаблона реализовать через архивирование; окончательное удаление истории — отдельное явное действие с подтверждением.

## 6. Выполнение тренировки на телефоне

### 6.1. Основной поток

1. Нажать Start workout и выбрать любой шаблон без привязки к дню недели.
2. Создать сессию `in_progress`; показать текущую тренировку, прогресс и карточки упражнений.
3. В активной карточке показать план, предыдущий результат с датой и номер текущего подхода.
4. Ввести фактические **Reps** и **Weight**, затем нажать **Log set**.
5. Сразу сохранить запись локально, обновить прогресс, показать статус синхронизации и запустить визуальный отдых. Не ждать сетевого round-trip для таймера.
6. По окончании отдыха показать **Rest complete**. Следующий подход не считается выполненным автоматически.
7. В конце пользователь нажимает **Finish workout**, видит итог и возвращается в историю/календарь.

### 6.2. Требования к вводу

- Рабочий экран помещается на ширину 360 px без горизонтального скролла. Проверить также 390 и 430 px.
- Основные touch targets — не менее 48 × 48 CSS px; числовые поля и кнопка сохранения доступны одной рукой.
- Вес: decimal keyboard, шаг ±0.5 kg по умолчанию с настройкой шага; повторы: integer keyboard, шаг ±1.
- Принимать `12.5` и `12,5` в UI, хранить число; JSON использует стандартную десятичную точку.
- После первого ввода подставлять значения предыдущего подхода этого упражнения, а для первого подхода — последнего включённого в статистику результата с совместимой convention. Показывать это как предложение, а не уже выполненный результат.
- Если истории нет: можно подставить верхнюю границу плановых повторов; внешний вес оставить пустым, bodyweight — 0. Пользователь подтверждает каждый подход отдельно.
- Фактические повторы могут быть ниже/выше плана. Значение 0 допустимо для неудавшегося подхода с явной отметкой Failed; пустое поле не является нулём.
- Фактический внешний вес может быть 0, но отрицательный разрешён только в bodyweight adjustment.
- Для `loadMode: none` скрывать поле веса и сохранять только показатели соответствующего типа; отсутствие веса не является ошибкой.
- Доступны Edit set, Delete set с Undo, Skip set, Add set, заметки упражнения и всей сессии.
- Пропуск и незаполненный подход не превращаются в запись `0 kg × 0 reps`.
- Дополнительный подход помечается Extra; исходное число запланированных подходов не меняется.
- Пользователь может перейти к другому упражнению и вернуться, не теряя ввод.
- Изометрия: поля секунд для Front / Back / Left / Right и кнопка **Log round**. Отдых начинается после целого круга, а не после каждого направления.
- Duration: поля времени и необязательного расстояния, кнопка **Log activity**; при нулевом отдыхе таймер не запускается.

### 6.3. Завершение, восстановление и несколько устройств

Состояния сессии: `in_progress`, `completed`, `abandoned`; удаление — отдельный soft-delete `deletedAt`.

- Разрешить завершить частично выполненную тренировку после сообщения о незавершённых подходах. Они сохраняются как пропущенные/невыполненные, без выдуманных результатов.
- Resume продолжает исходную сессию. Abandon сохраняет её в истории с соответствующим статусом; по умолчанию она не участвует в аналитике.
- Один основной активный workout на аккаунт. При запуске второго предложить Resume или Abandon current; использовать online transaction для указателя `activeSessionId`.
- Для MVP начало новой сессии требует сети. Уже загруженную активную сессию можно продолжить при временном обрыве.
- При refresh, уходе на другую страницу, блокировке экрана и повторном открытии с сетью восстановить локально записанные подходы, неотправленные изменения и состояние отдыха.
- Использовать стабильный `setId`/`roundId` и идентификатор операции: двойное нажатие и повтор синхронизации не создают второй подход.
- Обычное чтение истории доступно на разных устройствах. Одновременное редактирование одной активной сессии не должно молча затирать данные: показать предупреждение о другом редакторе, предоставить явный takeover, проверять revisions при конфликте. Для offline-конфликта сохранить локальный вариант до решения пользователя.
- Статусы **Saved locally**, **Syncing**, **Synced**, **Sync failed — Retry** должны отражать действительность. Firestore server acknowledgment отличать от локального принятия записи.
- При выходе не терять неотправленные записи молча; предложить синхронизировать/отменить выход. Локальные данные и подписки должны быть изолированы по UID и очищены/недоступны следующему аккаунту.

Offline-ориентир: [Firestore offline data](https://firebase.google.com/docs/firestore/manage-data/enable-offline). SDK cache не освобождает от обработки отказа записи и конфликта. Холодный запуск сайта совсем без сети и service worker не являются обязательством MVP.

## 7. Визуальный таймер отдыха

У каждого задания есть `restSeconds`. UI: крупный MM:SS, прогресс-индикатор и название следующего действия. На телефоне таймер остаётся видимым при прокрутке и не перекрывает ввод.

Правила:

1. Запускать после успешной локальной фиксации нового подхода/круга/активности, если `restSeconds > 0`. Не запускать на изменение input и при ошибке валидации.
2. Сохранить `startedAt`, `deadlineAt`, исходную длительность и ссылку на вызвавший запись set/round/activity. Остаток считать как `max(0, deadlineAt - now)`, а не уменьшать счётчик на каждой итерации.
3. При возвращении из фона пересчитать остаток по времени. Истёкший таймер показывать как Rest complete, без отрицательных значений.
4. Управление: **Skip rest**, **+30 sec**, **Restart rest**. Пользователь может начать следующий подход до окончания отдыха; новая подтверждённая запись заменяет активный таймер.
5. Редактирование старого подхода, синхронизация, повтор запроса, переход по страницам и загрузка истории не перезапускают таймер.
6. Undo только что записанного подхода отменяет связанный с ним текущий таймер. Удаление другого старого подхода не влияет на отдых.
7. Таймер запускается и после последнего записанного подхода, пока сессия активна; Finish/Abandon его останавливает.
8. При добавлении прошлой тренировки таймер выключен.
9. Только визуализация: без звука, вибрации, push, обязательного wake lock и серверных timer jobs. Работа JavaScript в фоне не гарантируется; корректное восстановление времени обязательно.

## 8. История и календарь

### 8.1. История

Список с пагинацией и фильтрами по дате, шаблону и статусу. Карточка: название snapshot, дата, длительность, выполненные подходы, статус и отметка исключения из статистики. Детали показывают все фактические записи и позволяют исправлять ошибки без запуска отдыха.

Доступно **Add past workout**: выбрать дату и шаблон, вручную заполнить результаты, сохранить как completed. В таком режиме длительность можно указать вручную или оставить неизвестной (`null`), не вычислять её из времени заполнения формы.

### 8.2. Календарь — отдельный обязательный экран

- Месячная сетка с днями недели, Monday-first, Previous / Next / Today и названием месяца на английском.
- Отметки тренировок внутри соответствующих дней. Для нескольких сессий — несколько маркеров/счётчик, без потери записей.
- Клик/тап по дню открывает список тренировок дня в панели или bottom sheet; тап по тренировке — её детали.
- Сегодня: Start workout / Resume. Прошлая дата: Add past workout. Будущие даты видимы, но создание завершённой тренировки в будущем запрещено; планирование будущих событий вне MVP.
- Различать completed, in_progress и abandoned. Исключённые из статистики тренировки остаются в календаре с меткой **Excluded from stats**. Soft-deleted скрыты.
- Сетка остаётся сеткой на телефоне; список выбранного дня дополняет её.
- Запрашивать данные видимого диапазона, включая показанные соседние дни месяца.

### 8.3. Даты и часовой пояс

В профиле хранить IANA timezone, первоначально из браузера, с возможностью изменить. Для сессии сохранять UTC timestamps, `timeZoneAtStart` и явный `workoutDate` в формате `YYYY-MM-DD`, вычисленный в этом часовом поясе при старте.

Календарь группирует по `workoutDate`: переезд/смена timezone не перемещает прошлые тренировки на другой день. Сессия через полночь относится к дню начала. Пользователь может явно исправить дату; это обновляет календарь и статистику. Проверить DST и переход месяца/года.

## 9. Прогресс и исключение выбросов

### 9.1. Что показывать

Общие фильтры: Last 4 weeks / Last 12 weeks / All time / Custom; тренировка; упражнение. По умолчанию — последние 12 недель. Пустое состояние отличается от нулевого результата; пропущенные даты не интерполировать как нулевой вес.

| Уровень | Обязательные показатели |
|---|---|
| Overview | Количество завершённых включённых тренировок; тренировки по неделям; число выполненных рабочих подходов; длительность при наличии |
| Workout | Хронология сессий этой программы; длительность; выполненные/запланированные единицы; повторы и подходы; переход к прогрессу каждого упражнения |
| Strength exercise | Max recorded load по сессиям; Best reps at selected load; total reps; external-load volume; таблица исходных подходов |
| Bodyweight exercise | Повторы, подходы и signed adjustment; отдельные режимы Bodyweight / Added / Assistance |
| Isometric exercise | Завершённые круги; секунды удержания по направлениям и суммарно |
| Duration exercise | Фактическая длительность; расстояние, если записано |

Для workout-показателей план брать из snapshot. Добавленные подходы показывать отдельно. Изменения состава программы обозначать на графике/tooltip: пользователь должен понимать, что сравниваются разные планы.

Формулы и правила:

- Завершённый успешный strength set: фактически залогирован, не deleted/skipped, `reps > 0`; failed с `reps = 0` сохраняется в истории, но не даёт PR или выполненный успешный подход.
- Total reps — сумма фактических повторов допустимых strength sets.
- Завершённый isometric round содержит фактическое положительное время для каждого запланированного направления; время вне целевого диапазона допустимо и остаётся фактическим результатом. Частичный круг виден в истории, но не увеличивает completed rounds. Duration block считается выполненным после явного Log activity с положительной фактической длительностью, даже если она отличается от цели.
- Max recorded load — максимум внешнего `weightKg` среди успешных допустимых подходов, с повторами в tooltip.
- Best reps at selected load — максимум повторов при выбранном весе, без смешивания conventions.
- **Logged load × reps (kg·reps)** = `sum(weightKg × reps)` для external-упражнения. Для гантелей это показатель по введённому весу одной гантели; автоматически удваивать его нельзя. Не складывать его в общий тоннаж разных упражнений и не выдавать за физическую работу.
- Для подтягиваний отрицательная помощь не создаёт отрицательный объём. Bodyweight volume/e1RM не рассчитывать. Показывать знак нагрузки и режим; помощь 20 kg и дополнительный вес 20 kg не объединять.
- Plan completion = завершённые исходно запланированные единицы / доступные исходно запланированные единицы. Strength — sets, isometric — rounds, duration — blocks. Исключённые упражнения удаляются и из числителя, и из знаменателя. Extra sets не увеличивают процент выше 100%; при пустом знаменателе — N/A.
- Workout count и duration зависят от включения сессии; исключение одного упражнения не удаляет сам факт выполненной тренировки. Если все упражнения исключены, workout остаётся в счётчике сессий, а показатели упражнений — N/A.
- Средняя длительность не включает `null`; abandoned/in_progress не смешивать с completed.
- История упражнения агрегируется по стабильному `exerciseId`, а не текстовому имени.

Все графики имеют единицы, легенду/подписи, дату, tooltip и доступную табличную альтернативу. Никаких автоматически придуманных результатов или автоматического удаления выбросов.

### 9.2. Четыре независимых уровня исключений

| Действие | Scope | Эффект |
|---|---|---|
| Exclude this workout session | Одна выполненная сессия | Вся сессия исчезает из статистики |
| Exclude this exercise in this session | Упражнение в одной сессии | Все его подходы в этой сессии исключены |
| Exclude workout from statistics | Шаблон программы | Все сессии этой программы исключены, включая будущие |
| Exclude exercise from statistics | Каталог упражнений | Упражнение исключено во всех программах и сессиях |

Использовать `excludedFromStats` и необязательный reason. В сессии scope упражнения — конкретный `sessionExerciseId`; если оно повторяется дважды, UI должен позволять выбрать нужное вхождение.

Допустимость записи для аналитики:

```text
session.status == completed
AND session.deletedAt == null
AND NOT session.excludedFromStats
AND NOT template.excludedFromStats
AND NOT exercise.excludedFromStats
AND NOT sessionExercise.excludedFromStats
AND record is not deleted or skipped
```

Для workout count применять только session/template условия. Архивирование не является исключением из статистики. Глобальные флаги читать из актуальных записей, а измерения — из snapshot.

Каждое исключение обратимо через **Include in statistics**. Возврат глобального флага не сбрасывает частные исключения. UI объясняет активную причину исключения и не позволяет создать ложное впечатление, что запись включена при оставшемся родительском исключении.

Изменение флага сразу пересчитывает все соответствующие карточки, графики, PR/max и предложения предыдущего результата. История/календарь/записи не удаляются. В Settings или Progress нужен список исключений с восстановлением. Фильтр **Show excluded** в истории показывает исходные данные; это не добавляет их в обычные агрегаты.

## 10. Модель данных и технические ограничения

Рекомендуемая структура Firestore; точные вспомогательные поля агент может расширять, сохраняя поведение:

```text
users/{uid}
users/{uid}/exercises/{exerciseId}
users/{uid}/workouts/{workoutId}
users/{uid}/sessions/{sessionId}
users/{uid}/sessions/{sessionId}/exercises/{sessionExerciseId}
users/{uid}/sessions/{sessionId}/records/{recordId}
users/{uid}/importReceipts/{operationId}
```

| Сущность | Минимальные поля |
|---|---|
| User | displayName, email, timeZone, units=kg, seedVersion, activeSessionId, settings, createdAt |
| Exercise | key, name, kind, loadMode, weightConvention, notes, archivedAt, excludedFromStats, timestamps |
| WorkoutTemplate | key, name, notes, version, ordered items с exerciseId/itemId/target/restSeconds, archivedAt, excludedFromStats, timestamps |
| WorkoutSession | templateId, templateVersion, nameSnapshot, workoutDate, timeZoneAtStart, status, entryMode=live/retrospective, startedAt, finishedAt, durationSeconds/null, excludedFromStats, exclusionReason, notes, timerState, revision, deletedAt, timestamps |
| SessionExercise | itemId, exerciseId, order, exerciseSnapshot, targetSnapshot, restSeconds, excludedFromStats, exclusionReason, notes |
| SessionRecord | sessionExerciseId, kind, plannedUnitIndex/null, isExtra, status=logged/failed/skipped, reps/weightKg либо holds либо durationSeconds/distanceKm, loggedAtClient, syncedAtServer, revision, operationId, deletedAt |
| ImportReceipt | operationId, fileDigest, createdIds/mapping, completedAt |

`holds` — значения секунд по направлениям; у session record одного вида отсутствуют несовместимые поля другого вида. Все timestamps аудита — server timestamps; время пользовательского действия хранить отдельно для offline-сценария.

Локальное хранилище IndexedDB/аналог: draft активной сессии, UID-scoped pending operations и timer deadline. Секундные обновления таймера не пишутся в Firestore. Поля фактического ввода отправлять на Log/Edit, а не на каждое нажатие клавиши.

Не хранить всю историю пользователя в одном документе. Предусмотреть индексы для диапазона дат, templateId + date и status + date, а также пагинацию. Для аналитики загружать ограниченный диапазон и строить агрегаты одной общей функцией; All time — постранично с состоянием загрузки. При малом объёме MVP не требуются отдельные микросервисы или scheduled aggregation jobs.

### 10.1. Доступ и безопасность

- Правила Firestore проверяют `request.auth != null` и `request.auth.uid == uid` для каждого пользовательского пути; default deny для остальных путей.
- Проверять типы/границы критичных полей, неизменяемые связи/владельца при update, доступ к подколлекциям. UI route guard не заменяет правила.
- Читать только коллекции своего UID. Не выполнять общий query всех пользователей с ожиданием, что rules отфильтруют результат.
- Firebase client SDK и browser APIs инициализировать только в браузере; не допускать SSR-ошибок `window is not defined` и разделяемого между пользователями состояния на сервере.
- MVP может читать Firestore напрямую из клиента под Security Rules. Если добавлены server endpoints/Admin SDK, каждый endpoint проверяет Firebase ID token и ownership отдельно.
- Не помещать service-account credentials в клиент, репозиторий, public env или import JSON. Публичный Firebase web config сам по себе не обеспечивает доступ к данным.
- Пользовательские названия/заметки выводить как текст, без исполнения HTML. JSON никогда не исполнять как JavaScript.

## 11. JSON-импорт программ

### 11.1. Пользовательский поток

1. Выбрать UTF-8 `.json` файл или вставить JSON в textarea.
2. Parse → schema validation → semantic validation. Никаких записей до успешной проверки всего файла.
3. Preview показывает названия программ, упражнения, планы, отдых, units и потенциальные конфликты.
4. **Import workouts** создаёт личные шаблоны. История выполненных тренировок через этот формат не импортируется.
5. Показать количество созданных программ и ссылку на Workouts. При ошибке не оставлять частично импортированный набор.

Ограничения MVP: файл ≤ 1 MiB; 1–20 workouts; 1–100 exercise definitions; 1–40 items на workout; имя 1–120 символов; notes ≤ 2000 символов; key — `[a-z0-9][a-z0-9-]{0,63}`. Ограничить итоговый сериализованный template payload до 64 KiB до записи в Firestore.

Импорт требует сети для финального commit. Валидация/preview могут работать локально. Для этих ограничений использовать один atomic commit/transaction, включая mapping и receipt; если операция превышает поддерживаемые лимиты, отклонить до записи и объяснить, как разделить файл. Ориентир: [Firestore transactions and batched writes](https://firebase.google.com/docs/firestore/manage-data/transactions).

Правила идентичности:

- `key` в JSON — переносимый ключ, а не произвольный путь Firestore, UID или owner.
- Все `exerciseKey` должны ссылаться на каталог внутри файла; duplicate keys и неизвестные ссылки — ошибка.
- Существующее упражнение с совпавшим key и совместимыми kind/load/convention можно явно сопоставить в preview. Не объединять автоматически только по похожему названию; не перезаписывать существующее имя/notes.
- При несовместимом совпадении предложить **Import as separate exercise** с новым внутренним ID/key; remap выполнить последовательно для всех ссылок этого файла. Либо отменить импорт.
- Шаблоны импортируются как новые. При совпадении имени/key показать предупреждение и предложить Import as copy; существующие шаблоны/историю не перезаписывать.
- Один submit имеет стабильный `operationId`; повтор после потери ответа возвращает результат этой же операции. Повторный намеренный импорт того же файла допускается только после предупреждения о копиях.
- Экспорт пользовательских данных не является обязательным MVP; **Download sample** и доступный schema-файл обязательны.

### 11.2. Контракт v1

Все имена полей — английские. Root:

| Поле | Тип | Правило |
|---|---|---|
| `schemaVersion` | integer | Ровно `1`; неподдерживаемая версия отклоняется |
| `units` | string | Ровно `kg` |
| `exercises` | array | Общий каталог определений внутри файла |
| `workouts` | array | Импортируемые шаблоны |

Определение упражнения:

| Поле | Обязательно | Значения |
|---|---|---|
| `key` | да | Уникальный slug |
| `name` | да | Название |
| `kind` | да | `strength`, `isometric`, `duration` |
| `loadMode` | да | `external`, `bodyweight`, `none` |
| `weightConvention` | да | `total`, `per_dumbbell`, `machine_stack`, `as_logged`, `bodyweight_adjustment`, `none` |
| `notes` | нет | Plain text |

Допустимые сочетания: strength/external + одна из первых четырёх conventions; strength/bodyweight + bodyweight_adjustment; strength/none + none. Isometric и duration в v1 используют none/none.

Workout: обязательные `key`, `name`, `items`; необязательные `notes`. Item: обязательные `itemKey`, `exerciseKey`, `target`, `restSeconds`; необязательные `notes`, `defaultWeightKg`. Порядок элементов массива — порядок выполнения. `itemKey` уникален внутри workout.

Форма `target` зависит от kind:

```json
{
  "strength": {"sets": 3, "repsMin": 6, "repsMax": 10},
  "isometric": {"rounds": 2, "directions": ["Front", "Back", "Left", "Right"], "holdSecondsMin": 5, "holdSecondsMax": 10},
  "duration": {"durationSeconds": 1500}
}
```

Это иллюстрация трёх вариантов, **не самостоятельный импортируемый файл**. В конкретном item поле `target` содержит только соответствующий объект, например `{"sets":3,"repsMin":6,"repsMax":10}`.

Валидация:

- `sets`/`rounds`: integer 1–30; плановые reps: integer 1–1000 и min ≤ max.
- `restSeconds`: integer 0–3600; 0 означает без таймера.
- Directions: 1–8 непустых уникальных строк; holdSeconds: integer 1–600, min ≤ max.
- Duration: integer 1–86400 seconds.
- `defaultWeightKg` разрешён только для strength с loadMode ≠ none; external: 0–2000, bodyweight: −2000…2000. При отсутствии поле опускается, не заполняется `null` или пустой строкой.
- Фактические значения имеют те же разумные границы; actual reps допускают 0 для failed, actual hold seconds допускают 0 для незавершённого направления. Нулевой незавершённый круг не считается выполненным.
- Никаких чисел в строках, NaN, Infinity, trailing commas, комментариев или unknown properties. Проверять `additionalProperties: false` на всех объектах schema.
- Trim имён/ключей; пустая строка после trim — ошибка. Пользовательские notes не интерпретировать как код.
- Ошибка включает путь и понятное английское объяснение: `workouts[0].items[2].restSeconds: expected an integer from 0 to 3600`.

Агент создаёт machine-readable JSON Schema из этого контракта и использует ту же модель для формы редактора, runtime-валидации импорта, sample JSON и документации. Семантические cross-reference проверки выполнять после schema validation.

При отдельной реализации четверга нужна ручная отметка разминочных подходов или предварительное уточнение их структуры; таблица выше сохраняет исходную информацию.

## 14. Визуальный стиль и доступность

Референс: [neubrutalism_ui](https://github.com/infm5/neubrutalism_ui). Создать собственные Svelte-компоненты с визуальными принципами референса:

- Светлый кремовый фон; чёрные контуры 2–3 px; жёсткие offset shadows без размытия; крупные понятные кнопки; насыщенные жёлтые, розовые, голубые и зелёные акценты.
- Читаемая типографика, хорошо различимые цифры и достаточный контраст. Цвет не является единственным сигналом статуса.
- Компоненты: Button, Card, NumberInput, Tabs, Dialog/Sheet, Toast, Timer, CalendarDay, StatCard, EmptyState, ChartContainer.
- На телефоне ввод подходов — карточки/короткие строки, не уменьшенная копия широкой бумажной таблицы. На desktop допустима табличная раскладка.
- Видимые focus states, labels для полей, клавиатурная навигация, accessible dialogs, reduced-motion. Не объявлять каждую секунду таймера через screen reader; озвучивать смену состояния.
- Клавиатура телефона и safe areas не закрывают Log set. Фиксированные панели не перекрывают последние поля/кнопки.
- Loading, empty, error, offline и sync-conflict states должны быть спроектированы, а не заменены alert/console.log.

## 15. Реализация, Firebase и Vercel

Разделить UI, доменные типы/валидацию, вычисление статистики, persistence и timer logic. Единая функция определения включения записи в статистику используется всеми экранами и previous-result suggestions.

Рекомендуемые области `src/lib`: components, domain, firebase, repositories, analytics, validation, seed. Не вводить отдельный backend без конкретной необходимости. Для схемы/валидации можно использовать совместимые JSON Schema/Ajv или Zod с генерацией JSON Schema; выбранный подход должен поддерживать один источник контракта.

В репозитории должны быть:

- приложение SvelteKit, lockfile и согласованные npm scripts;
- `firestore.rules`, `firestore.indexes.json`, `firebase.json` и Emulator Suite configuration;
- `.env.example` без секретов;
- seed bundle с ровно пятью программами;
- `workouts.schema.json` и `workouts.example.json`, доступные из страницы справки;
- README: локальный запуск, эмуляторы, конфигурация Google auth, переменные Vercel, deploy rules/indexes, сборка/проверки, известные ограничения.

Переменные web-конфигурации, например:

```dotenv
PUBLIC_FIREBASE_API_KEY=
PUBLIC_FIREBASE_AUTH_DOMAIN=
PUBLIC_FIREBASE_PROJECT_ID=
PUBLIC_FIREBASE_APP_ID=
```

Дополнительные параметры Firebase добавлять только по фактической необходимости. Названия public env согласовать с SvelteKit. Настройки эмулятора по умолчанию выключены в production. Service account не нужен для стандартного клиентского доступа.

Deployment checklist:

1. В Firebase создать Web App, включить Google provider и Firestore; выбрать регион осознанно.
2. Развернуть rules/indexes отдельно от сборки сайта; не оставлять test-mode rules.
3. Добавить production domain и нужные стабильные staging/local domains в настройки Google/Firebase auth. Не полагаться на то, что любой случайный Vercel preview URL уже авторизован.
4. Настроить environment variables для нужных окружений Vercel; preview желательно направить на отдельный Firebase project, без production-данных.
5. Зафиксировать поддерживаемую Node version, подходящую выбранным версиям SvelteKit и Vercel. Проверить прямое открытие вложенных routes и refresh.
6. Сборка не требует записей в локальный диск на сервере и постоянно работающего процесса. Firestore хранит данные независимо от Vercel deployment.
7. Проверить Google login и базовую запись данных на реальном целевом домене. Успешный localhost build не считается проверкой OAuth production.

Агент не должен объявлять приложение развёрнутым, если не получил deployment URL и не проверил его. Если владельцу нужно вручную задать Firebase/Vercel credentials, завершить код и предоставить точные оставшиеся действия.
